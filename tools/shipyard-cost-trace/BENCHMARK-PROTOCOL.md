# Shipyard cost-trace benchmark protocol (provisional)

This protocol separates kernel correctness from production-system performance. It is a test plan, not a result report. Do not publish speedups, savings or industry-ranking claims until benchmark artifacts and the baseline outputs exist at the exact same code/data revision.

## 1. Benchmark layers

### A. Accounting/reconciliation correctness (required before any performance comparison)

Freeze a manifest of input event fixtures and expected outputs. Each fixture must state whether values are synthetic or from a permissioned source, plus its corpus SHA-256, source/rights reference, configuration revision, quantity axis and currency denomination. Keep expected results hand-calculated or generated by a small independent evaluator that does not import production aggregation logic.

Minimum valid fixtures:
- planned, simulated and observed hours with explicit missing stages;
- multiple tasks and quantity axes in one build;
- invoice line plus credit note, including exact signed minor-unit total;
- a rate-card estimate alongside the corresponding observed quantity and a separately recorded invoice actual;
- material issue, return, scrap and rework as different event meanings;
- partial execution with unknown remaining work;
- changed configuration / revised plan while preserving the original history;
- additive delta versus cumulative snapshot, including exact 12 → 14 snapshot = 14 and 12 + 14 delta = 26 expectations;
- correction replaces exactly one earlier delta, reversal cancels exactly one earlier delta, and duplicate delivery is rejected by stable source identity;
- event-time and recorded-time cutoffs, including a late arrival that must not change an earlier recorded-as-of result;
- source-record IDs and stream/sequence lineage carried into the normalized result.

Minimum invalid controls:
- duplicated event and transaction IDs or source stream sequences;
- cumulative snapshot passed straight to the additive audit reducer;
- mixed snapshot/delta semantics, multiple snapshot streams for one identity, contradictory snapshot sequence/time, or multiple corrections/reversals for one target;
- unresolved, cyclic, cross-build or cross-configuration lineage;
- observed actual entered at a planned/simulated stage;
- unresolved permission, absent source reference or malformed configuration digest;
- wrong quantity unit or mismatched currency basis / minor-unit exponent;
- non-finite quantity/rate and integer or derived-cost overflow;
- missing plan that would otherwise be silently coerced to zero.

Acceptance: exact agreement for all hand-calculated fields, all frozen negative controls rejected, zero unknown-to-zero coercions, and no merged estimate-plus-actual "grand total". Hash the fixture manifest and publish the exact test command and toolchain.

### B. Kernel performance (not shipyard productivity)

Record median and p95 end-to-end audit latency, peak resident memory when measurable, event count, number of edges, maximum lineage depth, number of distinct build/config/task/axis/basis groups, event-order seed, toolchain and hardware/runner metadata. Include both chained lineage and broad shallow graphs; a long chain alone is not a representative workload.

Required scales: 20, 200, 2,000 and 20,000 events. Add stress points only after the required scale runs reproducibly. Run multiple fresh processes, publish raw samples and the summary method. Keep correctness checks enabled for every timing run. Repeat the same input after permuting record order and compare the canonical report digest.

Do not compare a local laptop run to a CI run as though the hardware were identical. A candidate stretch target is p95 under 1 second for a 20,000-event audit on a declared two-vCPU reference runner; first establish repeatable baselines, and reject the target if measurements or complexity analysis show it is inappropriate. This threshold has not been measured.

### C. Schedule and disruption decision quality (future layer; outside this ledger crate)

Use identical, versioned job-shop scenarios with explicit precedence, worker/skill qualifications, equipment capacity, block-space geometry, material availability, inspection gates and due dates. Include at least:
- no disruption;
- machine/worker outage;
- late material arrival;
- rework discovery after inspection;
- a change to vessel configuration or work package;
- combined disruptions and recovery.

Use public generic scheduling benchmarks as an external solver-quality check before claiming any shipyard-specific advance. The [ScheduleOpt/JSPLib benchmark library](https://scheduleopt.github.io/benchmarks/jsplib/) maintains instances, a best-known-bound archive and standardized 10-minute comparisons among CP Optimizer, CP-SAT and OptalCP, with MIP results also represented. The [flexible-job-shop library](https://scheduleopt.github.io/benchmarks/fjsplib/) adds flexible routing cases. Freeze the benchmark revision, report per-instance lower/upper bounds and optimality gaps, and do not cherry-pick only instances where the new method wins. These public machine/job instances do not include shipyard block geometry, crane travel, spatial occupancy, material arrivals or inspection logic; passing them is solver-comparison evidence, not shipyard validation.

Compare at least four baselines:
1. frozen yard plan / current manual plan when permissioned data exists;
2. a simple transparent rule baseline (e.g., earliest-due-date with precedence and resource-feasibility checks);
3. a critical-path / resource-constrained project scheduling baseline;
4. a strong constraint/optimization baseline (MILP or CP-SAT for bounded instances; a declared heuristic for larger instances).

Report makespan, weighted tardiness, overtime, work-in-process, setup/changeover, resource utilization, material waste, rework/inspection escapes, constraint violations, recovery time after disruption and decision latency. Score only feasible schedules; report infeasibility rate and invalid/unsafe proposals separately. If a baseline times out, record its time limit and best feasible incumbent rather than discarding the result.

### D. Physical design and operations (separate validation domain)

Hydrodynamic resistance/propulsion, stability, structural design, maneuverability, safety and certification require their own validated models and test evidence. Compare CFD/propulsion work to applicable ITTC benchmark cases and test conditions. Report speed, draft, trim, displacement, loading, environmental conditions and uncertainty. An improvement at one design point must not be presented as whole-voyage fuel savings.

## 2. Fair comparison rules

- Freeze input corpus, train/tune/test partition, constraints, evaluation code and baseline configuration before comparing methods.
- Tune on a development set only. Keep a hidden or sealed test set for the final comparison; do not revise expected outcomes after seeing candidate results without a versioned correction.
- Match vessel class, work scope, price year, currency, region, service life, throughput, tax/tender scope and allocation policy for cost comparisons.
- Keep planned quantities, simulated estimates, observed quantities, rate-card estimates and posted financial actuals as separate fields. Before source ingestion, classify each quantity as additive delta, cumulative snapshot, correction or reversal; preserve event time and recorded time. Normalize by an explicit cutoff and preserve source-record lineage. The V0 audit now explicitly rejects records typed as cumulative snapshots; see [SHIPYARD-EVENT-SEMANTICS-001 #2458](https://github.com/Luminous-Dynamics/symtropy/issues/2458).
- Report unknown and unallocated amounts explicitly. Never infer a zero from absent evidence.
- Report point estimate, interval and uncertainty/calibration method when the evidence supports them; otherwise mark the uncertainty as unquantified.
- Retain failures, timeouts and negative controls in the report. Publish raw outputs and environment metadata, not only a headline score.
- A source link is not authentication, a permission flag is not legal review, and a passing unit test is not independent verification.

## 3. Outcome evidence needed for an industry claim

A claim that the method improves shipyard performance requires permissioned, longitudinal, build-level data and a declared baseline across more than one schedule or vessel. Pre-register the outcome definitions. Track total cost per accepted useful service unit, schedule adherence, labor hours, rework/scrap, safety/quality escapes, energy/fuel where relevant, service availability and uncertainty. Control for vessel class, production volume, learning effects, design changes, inflation, purchasing changes and work scope. Publish negative outcomes and exclusions.

Do not equate:
- deterministic arithmetic with measurement accuracy;
- digital-thread completeness with physical truth;
- schedule adherence with lower whole-life cost;
- lower modeled hull resistance at one point with a fleet-wide fuel reduction;
- test coverage with real-world validity.

## 4A. Spatial feasibility composition

The separate [space-time reservation verifier PR #2548](https://github.com/Luminous-Dynamics/symtropy/pull/2548) covers finite-yard bounds, rectangular block occupancy, declared transfer/access corridors, exclusion zones and exclusive vehicle timing. It is a feasibility oracle, not a planner. Keep its supported geometry/time profile and independent constraint receipt separate from this ledger's cost arithmetic. A proposed schedule should qualify only if both independent layers accept their respective inputs; then actual normalized work/financial records can be reconciled against the plan. A passing space-time verifier does not prove crane/lift safety or the physical yard geometry, and a passing cost ledger does not prove the schedule feasible.

## 5. Cross-repository ownership (provisional)

- **Symthaea** owns vessel requirements, model assumptions/applicability, physical-model evidence, uncertainty, and comparable source-pinned acquisition/lifecycle-cost inputs. It must not infer certified structural, stability, hydrodynamic or fire-safety facts from schedule output.
- **Symtropy** owns the manufacturing/digital-twin planning layer: work packages, precedence, yard-space/resource constraints, schedule/disruption alternatives, and the trace from planned/simulated quantities to normalized observations and financial actuals.
- **Mycelix** owns permissioned provenance/custody/inspection evidence and source-profile mapping, preserving original event time separately from repository/ingestion time and reporting lossy field mappings instead of silently upgrading claims.
- **Sol Atlas** may own spatial/source freshness context for sites, access, geography and material logistics; those layers provide context, not implicit manufacturing or certification authority.

Cross-repository links must bind exact configuration/schema/profile digests and distinguish forecast, simulation, provider assertion, observed measurement, independent verification, and formal approval. A link or signed receipt proves provenance of a claim, not truth of its physical content.
