# Symtropy Energy Dispatch Independent Audit v0.1

This small, standalone Rust crate provides an independent audit of the **finite integer-quantized electrical schedule** emitted by Sol-Atlas's energy_dispatch_assess CLI.

It is intentionally independent of the optimizer's transition/search implementation. It rechecks each returned alternative against the raw dispatch request: input identity, chronological interval alignment, source bounds, outage grid restrictions, served/unserved demand, battery state transitions and efficiency arithmetic, charge/discharge limits, terminal reserve, bus energy balance, and objective totals. It also verifies the run receipt's SHA-256 binding to the exact request bytes and the compact serialized assessment.

## Run

    cargo test --manifest-path tools/energy-dispatch-audit/Cargo.toml

    cargo run --manifest-path tools/energy-dispatch-audit/Cargo.toml --bin symtropy-energy-dispatch-audit -- \
      tools/energy-dispatch-audit/fixtures/pv-outage.request.json \
      path/to/energy-dispatch-run-report.json

The run report is the JSON output emitted by Sol-Atlas's energy_dispatch_assess CLI, including both receipt and assessment. The CLI prints a machine-readable audit report; exit code 0 means receipt integrity, schedule invariants, and applicable bounded-reference checks pass, 2 means audit failure, and 3 is reserved for an unknown status.

The additional Rust binaries `energy_candidate_schema_validate`, `energy_compilation_receipt_verify`, and `energy_audit_report_gate` support the cross-repository workflow. Schema validation uses pinned Rust crate versions (`jsonschema = 0.60.0`, `serde = 1.0.229`, `serde_json = 1.0.154`, `sha2 = 0.10.9`); request/config digests are checked by reserializing typed Rust structures instead of relying on cross-language JSON re-serialization. The end-to-end workflow covers the three reference templates plus the complete 36-point Symthaea PV/battery/grid sizing sweep. Symthaea creates the sweep once and materializes each exported candidate from that same in-memory result. The three reference templates have exact known-answer feasible-schedule counts and objective frontiers pinned at 1, 1, and 14; each of the 36 sizing variants must also pass its own independently enumerated feasibility/frontier comparison. The manifest gate requires every expected sizing tuple exactly once, zero dropped/rejected candidates, matching exported candidate documents, and an explicit synthetic-only claim ceiling. The Rust benchmark-ledger binary (report schema v0.6) records raw-input/report SHA-256 values, solver and independent-reference expansions, frontier sizes, source heads, and per-case schema/compile/dispatch/audit runtimes. It preserves the original 39-candidate sizing sweep and adds separate non-zero-economics, actual three-interval dispatch, five-case actual-dispatch panel, South African tariff-reference, and 195-row candidate × scenario matrix contexts. The matrix transforms every one of the three templates and 36 sizing tuples across nominal, PV-total-loss, early-outage, essential-demand-2x, and terminal-reserve-1 scenarios; each row binds the parent/child candidate, transform receipt, raw and typed mapping config, compilation, exact dispatch request/report, independent audit, and per-phase timings. Any missing, failed, or unknown row makes the gate fail and preserves its row-level status rather than disappearing from the denominator. The tariff context is explicitly candidate-only and carries unresolved source conflicts; it is not a customer bill. All scenario results are finite synthetic model evidence, not site resilience or an outage-probability claim. Sizing generation time is explicitly amortized from the single shared manifest export.

## Frozen fixture and tests

fixtures/pv-outage.request.json is copied from the synthetic Sol-Atlas request fixture at sol-atlas-core/schemas/examples/energy-dispatch-pv-outage.synthetic.json, source blob SHA d6c93b4448c8355c2732049ea9b3d133ee782b41. It declares two 1-hour intervals: 2 kWh of PV supply followed by 2 kWh of essential load during a grid outage, served by an idealized lossless 2 kWh battery.

Tests build a synthetic known-answer report locally to exercise the auditor, then apply negative controls for grid import during outage, forged state of charge, changed request bytes, stale report digest, and incomplete solver claims. The test-generated report is **not** an output produced by running the Sol-Atlas optimizer. A separate exhaustive enumerator independently recovers the 14 feasible complete schedules and three non-dominated objective vectors for this tiny case. The reference enumerator also has a deterministic 128-case generated suite checking repeatability and non-dominated frontier invariants, plus fail-closed budget/depth controls. The new `fixtures/three-interval-stress.request.json` extends this reference corpus beyond two intervals: one PV-surplus interval, one grid outage with critical demand, and one recovery-load interval with explicit synthetic cost/carbon factors. `fixtures/three-interval-stress-known-answer-v0.1.json` freezes the expected 9 feasible complete schedules and four-objective-vector Pareto frontier; `reference.rs` checks the multi-interval reference enumeration against that fixed answer. This remains finite-model evidence and does not imply a completed Sol-Atlas end-to-end run for the three-interval case. Those property checks test the reference implementation; they are not a substitute for differential tests against actual Sol-Atlas reports. Reference enumeration is limited to at most 64 intervals and 100,000 separately counted expansions; exceeding either limit is UNKNOWN, never PASS. The 36-case integration sweep is a search-space throughput/correctness benchmark, not a real-site performance comparison. Per-case process timings exclude one-time dependency compilation and runner provisioning; they should only be compared with future runs on matched runner classes and identical pinned inputs. The standalone workflow compiles/runs this auditor's tests. The separate Energy Studio End-to-End Bridge workflow is designed to consume actual Symthaea CLI output for all three reference architectures (grid-only, PV+grid, PV+battery+grid), validate each candidate against the pinned Symtropy schema, compile each through Sol-Atlas, run the exact dispatch CLI, and audit each actual report. Expected feasible complete-schedule counts are frozen at 1, 1 and 14 for these synthetic cases. Its cross-repository run is not yet verified passing.


## Candidate × scenario robustness matrix (195 required rows)

The separate candidate-level scenario profile is `fixtures/energy-candidate-scenario-panel-v0.1.json`. The transform binary `energy_candidate_scenario_transform` writes a candidate plus a receipt containing exact parent/child SHA-256 values, profile digest, scenario/candidate identity, applicability, and every JSON Pointer before/after mutation. The matrix runner applies those transforms to all 39 source candidates, then runs schema validation, Sol-Atlas compilation, typed receipt verification, actual dispatch, and the independent audit for each row. It records a per-row status even on failure.

The aggregate gate `energy_candidate_scenario_matrix_gate` requires 39 candidate IDs × 5 scenario IDs = 195 unique pairs. It reconstructs each child from the parent and receipt, validates scenario semantics (PV loss, outage/resource alignment, only essential demand doubled, or reserve claim), binds the exact mapping config both raw and typed, and requires the solver's feasible schedule count/frontier to match the independent audit. Matrix report v0.2 preserves the full solver and independently recovered Pareto objective vectors per row, not merely their counts. The v0.6 benchmark ledger deserializes and compares those vectors again, and rejects missing/mismatched vectors or count disagreements. Missing or failed rows are represented as failed/unknown and cause a non-zero gate result. The ledger includes all row receipts and cannot publish a successful result if any row is absent or unqualified.

The next workflow step runs `energy_candidate_robustness_report` only after the matrix gate passes. It emits `robustness-report.json`, bound to the exact matrix report and pinned scenario-profile digests. For each candidate it preserves all five scenario frontiers, derives per-scenario axis-wise best values, derives a worst-case-of-per-scenario-best envelope, and reports strict envelope dominance, equal envelopes, and incomparable candidates without weights. A coordinate-wise envelope may combine values from different frontier points; it is explicitly not described as a jointly attainable dispatch schedule. The main v0.6 benchmark ledger independently rechecks the robustness artifact's input hashes, full scenario frontiers, per-scenario axis-best calculations, worst-case envelopes, coverage, and reciprocal dominance/equality/incomparability relations. The derived artifact is uploaded with the raw matrix and its receipts.

After the v0.6 ledger validates the matrix and robustness report, `energy_search_policy_replay` evaluates cached-outcome discovery curves at 1, 3, 6, 12, 24 and 39 unique candidate proposals. It compares the reference-template-plus-Symthaea-manifest order, lexical order, a declared battery/PV structural heuristic, and 30 fixed seeded random-without-replacement orders (33 policy runs total). Across the 30 random seeds it emits nearest-rank p10/p50/p90 and min/max summaries for frontier-vector recall, worst-case essential unserved quanta, essential-service gap and cost gap at every budget. Metrics are candidate-envelope frontier-vector recall and objective-by-objective gap to the exact 39-candidate envelope oracle. The report is digest-bound to the ledger, matrix, robustness output and design-space manifest; the end-to-end artifact retains its report, qualification log and checksum receipt. This is **offline replay of already-evaluated candidates**: it measures discovery quality by proposal count, not online dispatch/search runtime, and is not a comparison against Symthaea's cognitive architecture search or industry tools. The full-domain budget must recover the full finite-domain envelope frontier and zero axis-wise gaps.

Expected operational output is 195 matrix rows plus 33 replay policy curves (three deterministic orders and 30 random seeds) at six budgets each, with a 30-seed quantile summary at every budget. No result or performance claim is made until CI executes the new Rust binaries. The work is tracked in [ENERGY-SEARCH-BUDGET-001 #2756](https://github.com/Luminous-Dynamics/symtropy/issues/2756) and [ENERGY-ROBUST-PROFILES-001 #2764](https://github.com/Luminous-Dynamics/symtropy/issues/2764).

## Five-case scenario resilience panel

`fixtures/energy-scenario-panel-v0.1.json` freezes a common three-interval synthetic request plus four exact transforms: total PV loss, an outage moved to the final interval, doubled essential demand during the outage/recovery intervals, and a one-quantum terminal reserve requirement. Each scenario includes its complete feasible-schedule objective multiset and derived Pareto answer. The standalone reference enumerator test runs all five cases; the end-to-end workflow materializes each request and answer from the frozen manifest, executes the actual Sol-Atlas dispatch CLI, independently audits the output, gates the known answer, and finally emits `scenario-panel-report.json`.

The panel-level gate verifies exact parent-to-child mutation receipts and rejects undeclared changes, then binds each actual dispatch report and audit to exact request bytes. It records scenario IDs/families, request/answer/report/audit/log hashes, feasible schedule counts, Pareto frontier agreement, audit check counts, and phase timings in the versioned benchmark ledger. The initial frozen answers are:

| Scenario | Feasible complete schedules | Pareto vectors |
|---|---:|---:|
| Nominal | 9 | 4 |
| Total PV loss | 3 | 3 |
| Outage shifted to final interval | 9 | 4 |
| Essential demand doubled in outage/recovery | 10 | 4 |
| Terminal reserve raised to one quantum | 4 | 2 |

These answers were derived for a tiny integer-quantized finite model, not a calibrated facility. The panel does not yet cover delayed/shortened solar windows at realistic time resolution, multi-hour/long-duration outages, battery degradation, stochastic probabilities, or real tariffs. Those remain next-step contracts rather than inferred features.

## Three-interval dispatch known answer

The end-to-end workflow now also runs the **actual Sol-Atlas dispatch executable** on `fixtures/three-interval-stress.request.json`, independently audits the output, and requires the solver frontier, bounded reference frontier and frozen answer to agree on 9 feasible schedules and 4 Pareto vectors. This is a separate context within report schema v0.3, so the original 39-candidate sweep count and timing definitions remain unchanged. Until a workflow produces the artifacts, this is a configured test, not a passing benchmark result.

## Non-zero economics stress context

The E2E workflow additionally transforms the exact generated `synthetic-pv-battery-grid` candidate into a named PV-availability stress case. The Rust transformer preserves the base-candidate SHA-256, the transformed-candidate SHA-256, the exact mutation path, and the before/after PV availability in a transformation receipt. It changes only the first-interval PV resource availability from 2 kWh to 1 kWh; the original neutral design and all 39 neutral-config benchmarks remain unchanged.

The transformed candidate is validated against the same pinned schema and compiled with a **separate explicit synthetic economics config** containing grid-cost units = 5 and carbon = 100 grams per declared grid quantum. These are test constants, not a tariff or a real grid emissions factor.

For this two-interval integer model, the independently frozen stress-case answer has 11 feasible complete schedules and five non-dominated service/cost/carbon/reserve objective vectors. The acceptance gate checks the base→transform receipt, exact candidate/config/request/report digests, Sol-Atlas frontier, independent enumerator frontier, and frozen known-answer vectors. The benchmark ledger records this context separately from the 39-case zero-cost sweep, including its own input/output digests and phase timings.

This is the first non-zero economic objective test, not a real economic ranking. A field or site study still requires sourced tariffs, jurisdiction-appropriate emissions data, realistic battery losses/degradation and a model validated for its claim scope. The follow-on multi-scenario economics and robustness plan is tracked in [ENERGY-OBJECTIVES-001 #2739](https://github.com/Luminous-Dynamics/symtropy/issues/2739).

The machine-readable public-input inventory is `fixtures/sa-facility-benchmark-source-registry-v0.1.json`, with the wider site-resilience plan in [`docs/engineering/SA_FACILITY_RESILIENCE_BENCHMARK_V0_1.md`](https://github.com/Luminous-Dynamics/symtropy/blob/research/energy-dispatch-independent-audit-v0-1/docs/engineering/SA_FACILITY_RESILIENCE_BENCHMARK_V0_1.md). It records the DFFE 2024 grid factors, the candidate 2026/27 City Power tariff sources, PVGIS v6 data boundaries, and the missing site inputs that block site-specific claims.

## South African tariff reference arithmetic

The standalone `energy_sa_tariff_reference` binary is a **source-bounded arithmetic check**, not a bill estimator. It consumes the provisional City Power Business Conventional 2026/27 candidate schedule and hand-calculated test cases under:
- `fixtures/energy-sa-tariff-schedule-2026-27.reference.json`
- `fixtures/energy-sa-tariff-known-answers-v0.1.json`

The fixture tests 2,600 kWh in low season and 1,200 kWh in high season, both using the candidate fixed-charge pair reported for the Business block tariff up to 100 kVA. Rates and amounts are represented as integer microZAR to avoid floating-point bill arithmetic. The calculator recomputes progressive energy-block usage, energy charges, monthly service charge, and a generic secondary fixed component, then checks the subtotal against hand-calculated answers. The second component is deliberately not labelled 'network' or 'capacity' in the generated arithmetic report because those source labels conflict. The code uses the R890.45 + R853.72 fixed pair shown by the municipal schedule and cross-checked by Focal Energy; it explicitly does not use the different >50-to-100 kVA pair published by Augos until that conflict is resolved. The calculator requires exact known-answer agreement before emitting a report and has a negative control for a modified expected amount.

The report explicitly carries `account_verified=false` and preserves the conflicting source interpretations in the benchmark ledger. The municipal budget annexure excludes a 6 c/kWh network surcharge while Augos lists a 6 c/kWh DSM levy; these are not assumed equivalent and neither is added. The municipal schedule and Focal Energy use a single fixed-charge pair for a business block tariff up to 100 kVA, while Augos describes separate <50 and >50-to-100 kVA fixed-charge bands and a different label for the second component. The ledger carries this conflict rather than silently selecting the Augos upper-band values. The 2% business/large-power-user surcharge and VAT are also not applied. Confirm the account's current approved tariff and all charges before using the arithmetic for any site bill or savings claim.

The end-to-end workflow runs this calculator and preserves the exact schedule, expected-answer fixture, output report, qualification log and file hashes as artifacts. This remains a public-source arithmetic test, not customer-specific tariff evidence.

## What a pass means — and does not mean

A pass means the exact request/report bytes match the run receipt, every returned schedule passes independently recomputed invariants, and the bounded reference enumerator agrees on feasible-schedule count and Pareto objective vectors. When reference enumeration completes, objective_claim_status = verified_for_bounded_model_case applies only to that finite request. When its separate expansion cap is exceeded, the aggregate status is unknown rather than a pass. Solver search_is_exact / pareto_frontier_complete flags are preserved as **solver-reported claims**; they are not the basis of the independent reference result.

The audit's exact reference enumeration is intended only for small finite integer cases. It does **not** establish AC power-flow feasibility, voltage/frequency stability, protection coordination, inverter dynamics, thermal/process behavior, real-world evidence truth, model calibration, hardware safety, field performance, or permission to actuate equipment. An unsupported physical/model requirement must remain outside the claim ceiling.
