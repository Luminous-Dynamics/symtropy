**Claim ceiling:** synthetic/evidence-bounded per-module lifecycle screen only

## Purpose

A module is not modular merely because it can be detached. It is modular when the complete service loop is better after accounting for safe isolation, access, diagnosis, removal, repair/replacement, reinstallation, configuration, post-maintenance testing, parts lead time and return-to-service evidence.

This adapter connects the EV carrier factory screen to module serviceability and whole-life economics. It does not create another factory model, maintenance ledger, digital passport, asset registry, battery model or service-release authority.

## Paradigm shift: restoration cost is a design variable

The evaluator is meant to make the following trade-offs visible before a vehicle/pod architecture is selected:
- integrated bay versus detachable pod versus mobile trailer versus AMR;
- common interfaces and fast swaps versus extra connectors, sealing, alignment and test burden;
- repair-in-place versus module replacement;
- initial module build cost versus replacement inventory, parts lead time and technician capability;
- fast field replacement versus the cost of maintaining duplicate modules and safe test fixtures;
- maximum fleet utilization versus inspection windows and maintenance reserve.

A detachable pod does not automatically reduce lifecycle cost. It must earn that claim through comparable task evidence, commonality, low rework, parts access and verified post-maintenance return-to-service.

## v0.1 factory composition

The CLI consumes the complete module factory report generated by PR #6193. It joins each row by `config_id`, checks the architecture identity and uses:
- target good modules per year;
- allocated incremental module-line equipment capex;
- module electrical and thermal energy per good module;
- factory capacity/status and the module production-release flag.

It does not recompute cell capacity or duplicate general factory overhead.

Run from the repository root after the factory overlay:

```bash
cargo run --quiet --manifest-path tools/ev-passenger-cost-frontier/Cargo.toml \
  --bin ev_carrier_lifecycle_screen -- \
  ev-carrier-module-factory-report.json \
  tools/ev-passenger-cost-frontier/fixtures/ev_carrier_lifecycle_v0_1.json
```

## Cost model

For each factory scenario and lifecycle profile, initial module manufacturing cost is:

[
C_{build}=C_{material}+
rac{t_{direct labor}}{60}r_{manufacturing}+
E_{electric}p_{electric}+
E_{thermal}p_{thermal}+
rac{K_{module factory}}{Q_{good modules/year},Y_{amortization}}
]

All terms use the declared USD currency-year. Missing tariffs, process energy, module throughput, equipment cost, amortization period or cost components prevent a complete build-cost claim.

Service paths carry explicit, ordered phases:
1. safe isolation;
2. access and disassembly;
3. diagnosis and inspection;
4. module removal (where applicable);
5. repair or replacement;
6. reinstall and reconfigure;
7. post-maintenance test;
8. authorized sign-off record.

For a path, service downtime is the sum of elapsed phase time plus explicit parts wait. Technician-hours are summed separately. Direct cost includes parts/consumables, any replacement-module charge and technician labor. The declared downtime value is kept separate and added only to the scenario cost comparison.

For a scheduled inspection count (n_s) per module-year:

[
C_{scheduled/year}=n_s(C_{labor}+C_{parts}+C_{downtime})
]

Unscheduled event frequency is never inferred from task examples. It is calculated only when both observed event count (N_f) and exposure (X) in module-years exist:

[
lambda_f=rac{N_f}{X}
]

The screen then compares repair and replacement paths under the same declared downtime value. The least-cost eligible path is chosen only when both choices are sufficiently evidenced or the alternative is explicitly blocked by a known hard gate. A stale/unknown post-test is not equivalent to a failed test, but neither is eligible for return-to-service.

The undiscounted horizon cost is:

[
C_{life}=C_{build}+H(C_{scheduled/year}+lambda_f C_{fault intervention})
]

The reported single-module maintenance-time fraction is:

[
U_{maintenance}=
rac{h_{scheduled/year}+lambda_f h_{fault intervention}}
{h_{operating/year}}
]

This is a **per-module maintenance time burden proxy**, not fleet availability, MTBF, reliability or mission success. It does not account for spare-module substitution, overlapping maintenance, carrier redundancy, route recovery or customer-service recovery. It is not a discounted NPV or a complete vehicle TCO.

## Evidence and status

- Synthetic values exercise arithmetic only.
- Measured or independent-test profiles still need source references and a complete task/equipment/configuration chain.
- Unknown task phases, event frequency, exposure, service evidence or post-test state remain unknown.
- A fault count without an exposure denominator is not a rate.
- A failed post-test blocks that path. Stale/unknown/mismatched evidence cannot be treated as a pass.
- The CLI never grants production release or return-to-service authority.
- A synthetic screen pass cannot be promoted into a physical maintenance-time or failure-rate claim.

The fixture deliberately contains two synthetic demonstration profiles (detachable pod and AMR handoff) and one integrated-bay profile whose manufacturing and lifecycle data remain unknown. The output matrix is 36 factory scenarios × 3 profiles = 108 lifecycle rows. The synthetic cost values are not vendor quotes, industrial-engineering estimates or design recommendations.

## Benchmark tournament and targets

Compare all architectures on the same mission and lifecycle boundary:
- truck-only carrier baseline;
- integrated enclosed bay;
- detachable pod;
- mobile drone-station trailer;
- AMR handoff module.

First compare each service task separately; then compare the per-module lifecycle vector. Future physical validation should report median, p90 and p95 phase times only when sample counts and censoring make those statistics meaningful. Report inspection, diagnosis, removal, repair, replacement, reinstall, parts wait and post-test separately.

Proposed acceptance targets:
- 100% declared service task/event accounting;
- 100% agreement with hand-computable synthetic cases;
- 100% deterministic results under profile and factory-row permutations;
- zero lifecycle totals when a required rate/exposure or cost boundary is unknown;
- zero return-to-service eligibility without exact ordered phases and fresh passed post-maintenance evidence;
- zero production release claims;
- no ranking where currencies, years, horizons, exposure denominators or service boundaries differ.

Do not claim superiority over published methods until the original instance, objective, vehicle/drone constraints and compute budget have been reproduced. Current matched comparison ownership is in #6247. Relevant published baselines include the 2026 shared-fleet allocation work using empirical drone energy/time regressions (Cicek et al., DOI [10.3390/drones10070476](https://doi.org/10.3390/drones10070476)) and the 2026 joint multi-truck/multi-drone fleet sizing and routing study (Xie et al., DOI [10.3390/drones10090658](https://doi.org/10.3390/drones10090658)).

## November 2026 research refresh and v0.2 implications

Two recent problem families change what a meaningful module-lifecycle benchmark must measure:

- Liang, Chen & Du, *European Journal of Operational Research* (online 15 October 2026), “Multi-visit truck-drone pickup and delivery problem with release dates and drone resupply,” DOI [10.1016/j.ejor.2026.10.020](https://doi.org/10.1016/j.ejor.2026.10.020), models distinct delivery and resupply drone classes, truck/locker/drone service, release dates, simultaneous pickup/delivery, time windows and payload/waiting-dependent drone energy. Its tailored ALNS reports paper-specific cost reductions against three baselines on its instances.
- Liu, Zhu & Zhang, *Transportation Research Part E* (November 2026), “Heterogeneous drone-truck routing problem with En-route operations,” DOI [10.1016/j.tre.2026.105114](https://doi.org/10.1016/j.tre.2026.105114), models heterogeneous aircraft, multi-visit sorties and en-route launch/recovery. It reports paper-specific makespan and energy improvements from these mechanisms.

These are algorithm/service comparisons, not measured lifecycle costs for our modules. They imply the next lifecycle benchmark should distinguish:
- delivery aircraft versus resupply aircraft as different configuration classes;
- maintenance and replacement cost per qualified service hour / successful on-time delivery, not only per module-year;
- maintenance-induced unavailability during rendezvous, multi-visit and resupply windows;
- serviceability of payload-handling, battery-removal, launch/recovery and reconfiguration interfaces;
- fleet heterogeneity and spare-module strategy, including the capex/maintenance effect of keeping multiple aircraft classes.

Keep the v0.1 claim ceiling unchanged: all current module rates, task durations, repair values and costs are synthetic. Do not import paper-reported cost or energy improvements into a module lifecycle result. Compose MFB #6177/#6147/#6247 and EV-ICD #6308 rather than implementing routing, cargo or interface qualification in this adapter.

## November 2026 battery-health and duty-cycle research refresh

Recent literature materially changes the v0.2 battery serviceability model. The lifecycle adapter should not treat a single scalar battery state-of-health (SoH) as a complete statement of mission capability.

### Two distinct health dimensions

- **Energy capability:** retained usable capacity/energy under the declared temperature, discharge-rate, age and mission profile. This constrains total sortie energy plus reserve.
- **Power capability:** resistance-derived power retention and voltage-sag margin under the peak current/power profile. A pack may retain reasonable capacity yet be unable to supply a short high-power demand safely.

Robin et al., *Scientific Reports* (published 14 October 2026), “Dual-health protocol modelling of Li-ion battery degradation for UAVs with capacity–resistance coupled metrics in aviation duty cycles,” DOI [10.1038/s41598-026-70252-8](https://doi.org/10.1038/s41598-026-70252-8), reconstructs 22 Sony–Murata VTC6 cells under different aviation duty protocols, reporting 439 valid capacity checkpoints, 388 impedance checkpoints and 415 paired health states. Its approach couples capacity retention and resistance-derived power retention; it also reports leakage-safe leave-one-cell-out validation. This is a useful benchmark design precedent, not a validated threshold set for our future pack.

### Degradation-aware mission allocation

Jiang et al., *Energy Conversion and Management* 348 (15 January 2026), Article 120778, “Battery degradation-aware vehicle routing problem for heterogeneous electric vertical takeoff and landing aircraft delivery fleets,” DOI [10.1016/j.enconman.2025.120778](https://doi.org/10.1016/j.enconman.2025.120778), uses a real battery-aging dataset and an ANN-derived degradation model in a MILP routing formulation. It reports, on its own instances and relative to its shortest-distance approach, 40.41% lower average degradation per kilometre, 53.26% greater average remaining useful life and 37.32% lower average maintenance and operational costs per kilometre. These figures are paper-specific; do not carry them into our architecture's claims or targets without reproducing its instances, data, objective, constraints and compute conditions.

The benchmark implication is to compare shortest-distance / minimum-energy routing with degradation-aware load balancing, and to report battery degradation per successful mission, flight hour and kilometre alongside service quality. A route can be energy-feasible today yet impose a disproportionate lifetime cost on a degraded aircraft or battery.

### Wind and configuration interaction

Wang et al., *Drones* 10(8), 627 (17 August 2026), DOI [10.3390/drones10080627](https://doi.org/10.3390/drones10080627), compares nine UAV configurations over 60 mFSTSP instances with 10, 25 and 50 customers and nine wind scenarios. It reports that wind changes both flight time and the feasible-sortie set, so cruise speed, battery energy and battery mass must be compared together; there is no universally best configuration. Its data-driven validation reports 3–6% deviation for makespan and energy under three wind conditions. Its simplifying assumptions include spatially uniform, time-invariant wind per scenario, so it is a baseline rather than a full spatiotemporal meteorological twin.

### v0.2 implementation requirements

1. Keep battery identity, cell/pack genealogy, service events and passport projection with Mycelix. This evaluator consumes typed evidence and does not create another battery registry.
2. Represent energy and power health as separate evidence-bearing quantities with measurement time, temperature, test protocol, instrument/calibration identity, sample count, uncertainty and configuration/serial effectivity.
3. Evaluate mission demand against both energy reserve and peak-power/voltage-sag envelopes. Missing, stale, incomparable or out-of-domain tests must produce indeterminate or blocked eligibility—not a nominal pass.
4. Preserve separate outputs for capacity fade, resistance/power fade, thermal derating, degradation increment, remaining-useful-life estimate and uncertainty. Do not average them into one health number that hides a binding constraint.
5. Model repair, replacement, balancing, reconditioning and remanufacturing as different interventions. Require a new post-intervention evidence chain and authorized sign-off; no algorithm may grant return-to-service.
6. Compose battery availability with maintenance windows, replacement inventory, charging queues, wind-feasible sorties and carrier/UAV co-availability through #6083/#6177. Do not duplicate dispatch or asset identity ownership.
7. Benchmark a shortest-distance baseline, energy-minimizing baseline, degradation-aware exact/MILP formulation on small instances, and a learned policy only after the deterministic baselines. Use held-out cells/batteries and duty cycles to prevent leakage.

### Proposed qualification metrics

- zero accepted dispatch proposals outside the independently supplied energy-reserve or peak-power envelope;
- zero health estimates accepted when serial, chemistry, test protocol, temperature range, calibration or sample lineage mismatches;
- exact agreement with hand-computable degradation and power-envelope cases;
- zero hidden failures when only one health dimension is supplied;
- report degradation per successful delivery, per flight hour and per kilometre, with uncertainty and service-level parity;
- report replacement/repair events, maintenance downtime, usable spare-battery inventory and energy/power constrained mission rejection separately;
- reproduce the cited paper's own result before comparing a proposed policy against it; only claim superiority on matched held-out cases with paired confidence intervals and identical hard constraints.

These are benchmark requirements, not evidence that a battery model, cell dataset, aircraft pack, or physical qualification campaign already exists in this repository.

## Battery service network extension (November 2026)

The module lifecycle screen must distinguish **a pack's serviceability** from **the network's ability to provide a qualified pack at the needed place and time**. This separation is now tracked by [BATTERY-SERVICE-NETWORK-001 #6674](https://github.com/Luminous-Dynamics/symtropy/issues/6674).

The new owner composes the v0.1 lifecycle output with finite, serialized battery inventory, charger/rack queues, fixed exchange points, mobile battery-service units, grid import limits, crew slots and weather/demand scenarios. It consumes lifecycle task evidence from this issue; it must not recreate inspection/repair events or infer that a pack is available merely because a replacement path is cheaper.

### New research baselines

- Xu et al., *Transportation Research Part D* 158 (September 2026), Article 105458, DOI [10.1016/j.trd.2026.105458](https://doi.org/10.1016/j.trd.2026.105458), model a closed-loop mobile battery swapping and charging network. Their three-level stochastic formulation jointly sizes the service network, allocates mobile swapping vehicles and jurisdictions, and allocates batteries and charging racks under demand/service/charging uncertainty.
- Xu et al., *Transportation Research Part C* (November 2026), Article 105855, DOI [10.1016/j.trc.2026.105855](https://doi.org/10.1016/j.trc.2026.105855), model a fixed/mobile swapping network and inventory with data-driven distributionally robust optimization, worst-case mean-CVaR and a joint chance constraint. Their abstract highlights that near-absolute reliability has a nonlinear infrastructure cost premium and that a flexible-only asset-light network may fail under extreme demand shocks.
- Ai et al., *Transportation Research Part E* 214 (October 2026), Article 104897, DOI [10.1016/j.tre.2026.104897](https://doi.org/10.1016/j.tre.2026.104897), integrate charging/swap locations, battery inventory and grid constraints.

These are road-EV infrastructure papers, not direct evidence about a UAV battery network. They supply optimization structures and failure modes to reproduce, not performance improvements that can be imported into our system.

This demonstrates that subscription utilization and pack-service economics matter alongside physical swap time. These are company-reported ePTW results. ### Lifecycle adapter contract

- This issue reports task-level safe isolation, inspection, removal, repair/replacement, reinstallation, post-test and sign-off burden.
- #6674 consumes these observations to model time-indexed pack states: installed, reserved, depleted, charging, cooling/balancing, inspection, quarantined, in repair, in transit, available or retired.
- A swap transaction does not make the removed pack immediately available. It becomes depleted/inspection/cooling/charging/quarantine according to confirmed events and evidence.
- An unconfirmed swap outcome requires reconciliation of physical custody and pack state before a second mutation. A timeout is not a completed swap.
- Network inventory cannot make an unqualified pack eligible; #6083 independently evaluates mission capability and permission.
- Simple repair, replacement, repurposing and remanufacturing remain distinct interventions. Passport status/lineage remains with Mycelix #6062/#6076 and must follow the finished-battery category/date rule.

The network target is lower wait and stockout risk at a lower full-lifecycle cost while preserving hard safety/evidence gates—not maximum swap count or maximum charger utilization.
