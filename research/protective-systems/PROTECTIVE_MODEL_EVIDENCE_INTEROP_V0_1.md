# Protective Model Evidence Interoperability v0.1

**Snapshot:** 16 November 2026  
**Owner:** PROTECT-MODEL-EVIDENCE-001 #5474  
**Parent:** PROTECT-RESILIENCE-MATCHED-EVAL-001 #5452  
**Status:** schema and synthetic conformance implementation; no live external-model adapter or external model validation

## 1. The paradigm shift

Do not build another model platform or require every specialist tool to adopt an Luminous-native data model.

Build a small, fail-closed evidence envelope around each specialist result. Preserve the model owner's original datasets, metadata, semantics and assumptions. Normalize only the minimum needed to compare provenance, rights, scope and artifact integrity.

The envelope is not a replacement for IN-CORE's dataset model, W3C PROV-O, RO-Crate, OGC API - Records, or a domain data format. It should be an adapter that can project into and out of those standards while retaining provider-native identifiers and fields.

## 2. Existing industry capability

### IN-CORE

IN-CORE is an established, open community-resilience environment with public Web Tools, Web Services, pyIncore and example Jupyter workflows. NIST describes Web Tools for browsing/searching datasets, hazards, fragility curves and repair curves, viewing metadata and visualizations, and downloading items where allowed. Its Joplin and Seaside testbeds are examples of existing community-scale modelling—not datasets or results that this fixture claims to have run.

IN-CORE's dataset API and analysis outputs already form a data-processing ecosystem. Our integration goal is to preserve those actual records and run relationships, not mimic a fictional IN-CORE result.

A comparative study published on 7 November 2026 inventories 24 infrastructure interdependency and enabling tools, with seven explicitly supporting cross-sector interdependency assessment in its energy/water/transport scope. It finds no tool dominates all dimensions and identifies a trade-off between model breadth, data burden, validation, integration and practical usability. This is why our adapter should complement specialist models rather than compete by recreating them. Source: Shamsi, Helmrich & Deegan, https://doi.org/10.1007/s10669-026-10162-2.

### W3C PROV-O: use the established provenance vocabulary

W3C PROV-O is a W3C Recommendation for expressing provenance through Entities, Activities and Agents. The minimum projection for a model run is:

- Dataset → prov:Entity
- Analysis execution → prov:Activity
- Provider organization/software/person → prov:Agent
- Activity consumes input → prov:used
- Output entity is generated by activity → prov:wasGeneratedBy
- Responsible provider/software → prov:wasAssociatedWith / prov:wasAttributedTo

**Critical negative rule:** do not infer that every output was derived from every input merely because one analysis consumed several input datasets and generated several outputs. W3C's provenance guidance explicitly says generation and usage alone do not imply all-to-all derivation. Emit prov:wasDerivedFrom only when a provider result or a more precise transformation record identifies the actual per-output dependency.

References:
- W3C PROV-O: https://www.w3.org/TR/prov-o/
- W3C PROV Working Group publications: https://www.w3.org/groups/wg/prov/publications/
- W3C PROV FAQ: https://www.w3.org/2001/sw/wiki/PROV-FAQ

### RO-Crate: package evidence for reuse

RO-Crate provides a standard JSON-LD structure for packaging datasets, files, software, workflows, people, organizations, licensing and provenance. As of this snapshot, RO-Crate 1.3 is the current long-term release, while 1.2 remains a stable release with the community working toward modularisation in RO-Crate 2.

Our envelope should be exportable as RO-Crate rather than inventing a rival research-object packaging format. Preserve the provider's original files, metadata and identifiers. Include local digests in the crate as integrity metadata, not as proof of scientific validity.

References:
- RO-Crate specification: https://www.researchobject.org/ro-crate/specification
- RO-Crate 1.2 introduction/provenance: https://www.researchobject.org/ro-crate/specification/1.2/introduction.html
- RO-Crate technical overview: https://www.researchobject.org/ro-crate/technical_overview

### OGC API - Records: geospatial discovery

OGC API - Records Part 1 Core (1.0.0) standardizes discovery and access to geospatial metadata records. This should be an optional catalog adapter for finding records and related resources, not a second spatial data store and not a replacement for the provider's actual data transfer mechanism.

Preserve coordinate reference identifiers exactly. Do not reproject coordinates, infer missing CRS or combine spatial datasets without an explicit, versioned transformation.

References:
- OGC API - Records: https://ogcapi.ogc.org/records/
- OGC Standard: https://www.ogc.org/standards/ogcapi-records/

## 3. Luminous evidence envelope

The v0.1 schema is:

research/protective-systems/schemas/protective-model-evidence-envelope-v0.1.schema.json

It fixes:
- evidence class and intended use;
- provider/platform, software version and documentation URI;
- analysis identity, run identity, execution state and timestamps;
- jurisdiction, context, boundary, scenario and time horizon;
- dataset IDs, direction, data type, semantic type, revisions and native units;
- coordinate reference state;
- rights/license metadata and permitted use;
- local artifact path, byte length and SHA-256;
- explicit dataset-to-analysis lineage edges;
- uncertainty status, representation, method and calibration reference;
- fixed claim ceiling.

### Rights and authority are distinct

A supplied LICENSED status and license ID are declarations, not independently authenticated grants. The v0.1 executable records whether the rights metadata is present and compatible with declared intended use. It does not verify the licence, provider identity, signature, terms of service or authority to redistribute.

A future policy must separately verify:
1. the source identity and run authenticity;
2. the license and rights scope for the exact use;
3. the data retention and redistribution restrictions;
4. the independent validity of the model output.

Unknown or restricted rights cause an abstention from external comparison. They must not be treated as public or harmless.

### Hashes and claim ceilings

SHA-256 checks that local artifact bytes match the declared digest and byte length. It does not prove who supplied the artifact, whether the upstream model ran, whether the model is accurate, or whether the physical world matches the model.

The current positive envelope disposition is intentionally bounded:

ENVELOPE_METADATA_COMPLETE_SOURCE_AND_RIGHTS_AUTHENTICITY_UNVERIFIED

It does not admit a result as a qualified real-world model output. Provider authentication and independent model validation are separate, future gates.

## 4. Synthetic compatibility fixture

The fixture files are:
- fixtures/protective-model-evidence-envelope-v0.1.json
- fixtures/model-evidence-payloads/synthetic-input.json
- fixtures/model-evidence-payloads/synthetic-output.json

The fixture is labelled synthetic, not executed and IN-CORE-shaped only. It is not generated by an IN-CORE service and must abstain from a model-performance claim. It has no external run ID, and its coordinate reference, revisions and uncertainty are explicitly unknown.

## 5. Conformance and adversarial tests

The Rust validator has 15 unit tests written, covering:
- synthetic envelope validates but still abstains from any model claim;
- byte tampering, wrong byte lengths and digest mismatch;
- duplicate dataset identities;
- input/output artifact direction and path reuse;
- incomplete, reversed and duplicate lineage;
- completed run without a run identity;
- unknown rights and unknown dataset revision;
- path traversal outside the fixture allow-list;
- represented uncertainty without method/calibration;
- a completed external-shaped record still cannot authenticate its provider;
- unsupported claim-ceiling escalation;
- intended-use/evidence-class mismatch.

Compilation, format, Clippy and tests remain unverified until the isolated hosted workflow completes. A test count is not a pass.

## 6. Benchmarking against the industry

The primary metric is not "number of adapters" or JSON schema validity alone. Measure whether evidence survives round-trips and whether unsafe/incomparable claims are blocked.

| Benchmark | Definition | Prospective target |
|---|---|---:|
| Required-field preservation | Required provider fields preserved or explicitly unknown | 100% |
| Artifact integrity | Correct byte length and SHA-256 on frozen fixtures | 100% |
| Lineage completeness | Every declared input/output is linked to the right analysis | 100% |
| False lineage | Incorrect or unproven derivation edges accepted | 0 |
| Unsupported rights admission | Unknown/restricted rights admitted for evaluation | 0 |
| Claim-ceiling escalation | Metadata envelope promoted to physical validation | 0 |
| Unknown-state fidelity | Missing provider fields silently replaced with defaults | 0 |
| Deterministic replay | Same frozen envelope and bytes produce identical report | 100% |
| Round-trip loss | Provider-native fields/IDs lost on export/import | 0 required-field loss |
| Operational burden | Human time and compute per successfully imported result | Measure, do not assume |

Test round-trip preservation across:
1. native IN-CORE dataset metadata → evidence envelope → native metadata projection;
2. envelope → PROV-O graph → envelope;
3. envelope + artifact files → RO-Crate package → envelope;
4. OGC API - Records metadata → context envelope, where the source is geospatial.

Do not require identical serialized JSON when standards use different representations; compare semantic fields, identities, units, rights and lineage.

## 7. How to beat the state of the art

A defensible improvement would be:
- no loss of critical provenance metadata across at least three independently maintained providers or standards;
- zero false lineage / false provenance on a frozen adversarial corpus;
- zero rights-state or claim-ceiling escalation;
- deterministic, explainable import reports with unknowns preserved;
- lower integration and review time than manually mapping provider outputs;
- no material performance or workflow burden that outweighs the evidence value.

These are future targets. The current v0.1 implementation only proves a narrow synthetic JSON fixture contract and local artifact integrity.
